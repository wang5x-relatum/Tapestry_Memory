# v0.1 contract draft

English | [中文](v0.1-contract.zh.md)

Status: proposed and not implemented; intended for version 0.1.0. The project name and bilingual strategy are decided, while the APIs and storage design below still require implementation and verification. This document is the behavioral contract source of truth; passing tests in the source project does not substitute for standalone-package acceptance.

## Scope

The first release focuses on embedded graph memory: nodes, edges, scopes, persistence, bounded relationship retrieval, and logical deletion. The target is Python 3.10+, the standard library, and SQLite without vendor APIs. The public package excludes host personality, value policy, model calls, conversation-source replay, and robot action orchestration.

The first release does not promise automatic relation extraction, automatic conflict arbitration, multi-device synchronization, distributed service operation, or arbitrary-scale performance. It will not impose a 500-character truncation: content limits require an explicit resource contract and must not inherit a host's input policy as a universal library rule.

## Data and identity

A node is expected to contain id, content, metadata, created_at, and weight; an edge is expected to contain source, target, relation, weight, count, and created_at. Exact types, ranges, time format, and mutation semantics must become an executable contract before coding; this field list is not yet a frozen schema.

Namespace must participate in storage identity and every read/write operation. Identical content across scopes must not share a mutable node; same-scope duplicate identity and metadata merge rules must be explicit. Do not carry forward a content hash as a global cross-scope primary key.

## Isolation and deletion

The suggested default scope is `default`; an empty value must not mean global access and should be rejected by explicit validation. Retrieval starts, each neighbor expansion, edge endpoints, results, and deletion must be scope-constrained. The first release will not provide implicit shared scopes; a library scope does not replace host authentication or authorization.

Deletion targets in-scope nodes, associated edges, and package-owned derived data; package caches must be invalidated. External source documents, host logs, backups, and storage-medium erasure are outside the guarantee. Do not promise “GDPR-complete deletion.” Writes need transaction boundaries, rollback on failure, and reopen-database verification.

## Provenance and retrieval

Metadata accepts JSON-serializable data; optional `provenance` lets a host locate original sources, and must round-trip losslessly through write, reopen, and retrieval. The package does not require `r:/c:` formats, read files or URLs automatically, or equate the presence of a source reference with truth verification.

The plan is to provide public write, retrieve, and delete entry points; exact signatures remain to be frozen. Do not publish installation or call examples that cannot run. Retrieval needs explicit `top_k`, traversal budget, ordering, and stability rules. When a budget is reached it must be observable, and partial results must not be presented as exhaustive search.

An optional matching callback remains vendor-neutral and the core is offline by default. Do not restore the host application's embedding switch; current internal experiments do not prove semantic benefit for a standalone package. If an external provider is added later, failure must be observable rather than silently substituting a test mock for real semantics.

## Implementation sequence and completion criteria

| Stage | Deliverable | Completion criterion |
| --- | --- | --- |
| Design baseline | Bilingual use cases, contract, and documentation rules | Review items are explicit; the checker covers the mechanical rules it claims |
| Core extraction | Standalone package, storage, and retrieval implementation | No internal-application imports, offline by default, public interfaces run |
| Contract acceptance | Unit and contract tests | Cross-scope identical content, cross-edge traversal, cross-scope deletion, transaction rollback, provenance round-trip, and database reopen are covered |
| Artifact acceptance | Wheel and sdist | Examples run after clean-environment installation; artifacts contain only allowed files and no databases, keys, or internal materials |
| Release review | License, version, documents, and benchmark record | User approves release; the exact verified artifact is published |

The first local commit establishes only the design baseline and documentation tooling; it does not mark core extraction complete. Do not use an empty directory count or document count as implementation progress.

## Benchmark and release boundaries

The source project's 73/90 result must not be presented as a standalone-package score. Any public benchmark must name the package version, sample selection, configuration, retrieval/generation/judging chain, and limitations. The historical 77.8% result was confounded by a timeout and does not prove semantic matching is harmful; later higher scores do not alone prove benefit. Do not enable semantic enhancement on that evidence.

The license and rights holder remain to be confirmed; there is no public remote repository, package release, or external support commitment yet. Do not write “open-source” as an already-granted license. Documentation pairing checks can be established independently; exploratory audits must not become release gates without validation.
